Documentación

Cómo funciona Alcy Legacy, qué calcula y qué limitaciones tiene este prototipo.

El problema Cómo se calcula el riesgo Modos de análisis Limitaciones Arquitectura real

El problema

Cuando alguien (o Bob) modifica código legacy — código viejo, sin tests, sin documentación — el riesgo real no es escribir el cambio, es romper algo silenciosamente que dependía de ese código, sin que nadie se entere hasta producción.

Alcy Legacy es un Skill de IBM Bob que evalúa ese riesgo antes de dejar que Bob modifique el archivo, y solo avanza si el riesgo está controlado o si ya se agregaron tests mínimos.

Cómo se calcula el riesgo

El cálculo es determinista — no es el modelo de lenguaje "opinando", es una fórmula fija y explicable:

Factor Condición Puntos
Cobertura de tests No se detectan tests que cubran el archivo +2
Dependientes 3 o más archivos dependientes +2
Dependientes 1 o 2 archivos dependientes +1
Antigüedad Último cambio hace más de 365 días +1

Riesgo bajo: 0–1 puntos · Riesgo medio: 2–3 puntos · Riesgo alto: 4+ puntos

Cada análisis muestra el desglose exacto de por qué llegó a ese resultado — la explicabilidad es un requisito de diseño, no un extra.

Modos de análisis

  • Modo demo: usa 3 archivos de ejemplo precargados, para una demo 100% predecible.
  • Archivo: subes un archivo objetivo y, opcionalmente, archivos de contexto y de test.
  • Carpeta: seleccionas una carpeta completa; se detectan tests por nombre automáticamente.
  • Proyecto (GitHub): se conecta en vivo a la API pública de GitHub para traer un archivo real de un repo y escanear hasta 25 archivos en busca de dependientes.
  • Solo documentar: corre el mismo análisis de riesgo pero se detiene ahí — genera funciones, clases e imports detectados y un reporte descargable, sin pasar por la simulación de cambio.

Limitaciones actuales del prototipo

  • La detección de dependencias usa coincidencia de texto (import/require), no un análisis real de compilador/AST.
  • La antigüedad en modo Archivo/Carpeta usa la fecha de modificación que reporta el navegador, no el historial real de git.
  • El modo GitHub no consulta el historial de commits todavía, así que no calcula antigüedad — se marca explícitamente como dato no disponible.
  • El "Paso 2 — Simular el cambio" es ilustrativo; en producción esa parte la ejecuta Bob directamente en el IDE.
  • El login es una simulación local en el navegador, sin backend ni almacenamiento real de datos.
  • El prototipo inserta datos del usuario (nombres de archivo, contenido) directamente en la página; la versión de producción sanitiza esos datos antes de mostrarlos, como corresponde a cualquier aplicación que maneja código de terceros.

De prototipo a producto real

Pieza del prototipo Equivalente en producción
Búsqueda de texto para dependientes dependency_scanner.py (análisis estático real)
Búsqueda en archivos de test coverage_checker.py
Fecha de modificación del navegador git_age.py (usa git log real)
Función computeRisk() en JS risk_score.py, invocado como archivo de soporte del skill
Consola simulada del Paso 2 Ejecución real en Agent mode, activada automáticamente por el Skill alcy-legacy

Según la documentación oficial de Bob, un Skill (no un modo custom) es la pieza correcta para esto: vive en .bob/skills/alcy-legacy/SKILL.md con un name y description en el frontmatter, y Bob lo activa automáticamente cuando detecta que la tarea coincide con esa descripción — justo el comportamiento de "interceptar antes de tocar código legacy" sin que el desarrollador tenga que cambiar de modo a mano. Los scripts del analyzer (risk_score.py, etc.) se agregan como archivos de soporte del propio skill, que Bob puede leer una vez activado.

Los modos custom de Bob (Agent/Plan/Ask + los propios) siguen siendo útiles para otra parte del flujo: por ejemplo, un modo "Legacy Reviewer" que el equipo activa manualmente para auditorías profundas, complementando al skill automático.

API

Referencia de la API planeada para la versión de producción de Alcy Legacy.

⚠ Roadmap — el prototipo actual corre 100% en el navegador y no expone estos endpoints todavía

Autenticación

Todas las peticiones requieren una API key en el header, asociada a la cuenta iniciada sesión.

curl https://api.alcylegacy.dev/v1/analyze \ -H "Authorization: Bearer LG_API_KEY"

Endpoints

POST/v1/analyzeAnaliza riesgo de un archivo objetivo
POST/v1/analyze/githubAnaliza un archivo dentro de un repo público
GET/v1/report/{id}Obtiene el reporte generado en Markdown/JSON
GET/v1/historyLista los análisis previos de la cuenta

Ejemplo — POST /v1/analyze

// Request { "target": { "name": "legacy_module.py", "content": "..." }, "context_files": [ { "name": "consumer_a.py", "content": "..." } ], "test_files": [] } // Response { "risk": "high", "points": 4, "dependents": ["consumer_a.py", "consumer_b.py", "consumer_c.py"], "has_tests": false, "reasons": [ "Sin cobertura de tests detectada (+2)", "3 archivos dependientes detectados (+2)" ] }

Integración con Bob

En producción, este endpoint es llamado directamente por el Skill de Bob como una tool antes de permitir un cambio en Agent mode — el mismo flujo que hoy simula este prototipo en el navegador.
